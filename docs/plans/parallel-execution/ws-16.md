## What it does (short)
A student's "saved / applied / not interested" on a recommendation, or "useful / not
useful" on a question, becomes one row per (student, memory, kind). Repeats return the
first row. Forgetting the memory deletes the rows through the FK cascade, inside the
forget transaction (I7). Nothing is applied anywhere (I6), and no memory content is
returned (I1).

The weekly report computes two of the five docs/04 pilot metrics. Each value comes
with its numerator, denominator and definition:
- saved-or-applied share over the openings alerted that week;
- question usefulness by first rating.
The other three are "TBD (pending data)", each with the reason. Weeks with fewer than
5 active students go to the gitignored `results/pilot/raw/<week>/`. The report holds
no ids, names or notes.

## Requests to other workstreams (exact payloads)
All calls are `POST /feedback` with `Authorization: Bearer <token>` and a JSON body:
```
{"target_memory_id": "<memory id, uuid4>", "kind": "<kind>", "note": "<optional, ≤ 280 chars>"}
kind ∈ "saved" | "applied" | "dismissed"              (target: an opening memory id)
     | "question_useful" | "question_not_useful"      (target: the asked memory id)
→ 201 {id, user_id, target_memory_id, kind, note, created_at}   new statement
→ 200 same shape, the FIRST row                                  repeat of (target, kind)
→ 404 unknown or another user's memory · 422 kind does not fit the target · 409 retry
GET /feedback[?target_memory_id=<id>] → 200 {"feedback": [rows, oldest first]}
```

**Bot (WS-10 files: src/ripple/notify/inbound/{keyboards,dispatcher}.py)**
- A new callback family `p`: `p:<code>:<memory id>`. Codes: `s` saved, `a` applied,
  `d` dismissed, `u` question_useful, `n` question_not_useful. At most 40 bytes, under
  Telegram's limit of 64. Add `feedback_data(memory_id, kind)` and decoding in
  `decode_callback`, mirroring `answer_data`.
- The dispatcher handles `p:` by calling
  `ripple.pilot.feedback.record_feedback(services.store, services.feedback_store, services.clock, user_id=<linked user>, target_memory_id=<id>, kind=<kind>)`.
  That is the same function the API uses, so no HTTP round trip is needed. Replies:
  - created: "Noted." For "applied", add "Ripple did not apply anywhere; this is for
    your records."
  - repeat: "Already noted."
  - `FeedbackTargetNotFoundError`: "That item is no longer available."
  - `FeedbackKindMismatchError`: log a warning and send no reply.
- `question_keyboard(memory_id)` gains a second row: `[Useful → p:u:<id>]`,
  `[Not useful → p:n:<id>]`.
- Alerts and digest items gain one row per opening: `[Saved → p:s:<id>]`,
  `[Applied → p:a:<id>]`, `[Not interested → p:d:<id>]`. Outbound alerts and digests
  send text only today (`Transport.send(chat_id, text)`, WS-6). Attaching keyboards
  needs a WS-6 contract change, e.g. an optional `reply_markup` parameter. Until then,
  only the question keyboard can carry feedback.

  student who lost their token cannot be erased without the author
  (docs/ops/incident.md). The admin CLI is WS-3/coordinator-owned; proposal:
  `revoke-token`, `issue-token`, `delete-user` (through the same path as DELETE /me).

  property for notes holds only in Postgres; this is tested by the slow test alone.

  DeprecationWarning in any test that builds a `Config`.
- **Not fixed from the review: minor 6.** "accounts" counts every users row, including

  says "accounts", not "enrolled".
