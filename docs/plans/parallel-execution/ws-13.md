## Open problems
- `rate_limit_guard` and `readiness_probes` each call `redis_factory`, so a process
  opens two arq pools; the `redis_factory` docstring says one pool shared by both.
  Build one `RedisPool` in `app_from_env` and pass it to both.
- The body-cap 413 lacks the security headers because `SecurityHeadersMiddleware` is
  inside `BodySizeLimitMiddleware`. Swapping their order (headers outside the cap)
  fixes it; add the assertion to `test_a_declared_body_over_the_cap_is_413...`.
- Only the resume confirm passes `current_trace_id()` to Intake. `POST /statements`
  calls `intake.ingest(statement)` without it, so those ChangeEvents have no
  `trace_id`; the docstring of `ripple.api.logging` says handlers pass it.
- A confirm that loses to a reject has already run Intake, so a memory can exist for
  a rejected candidate (ADR-0096). The race test asserts statuses only.
- `PostgresCandidateStore.replace_candidate` with `expected_status` returns silently
  when the row vanished; the in-memory fake raises `KeyError`.
- The digest and alert jobs take no per-user lease; two workers can both send
  (ADR-0095). Fine with one worker.
- The Telegram bot's `RateLimiter.allow(key, limit, window)` (ADR-0076) has no Redis
  implementation; `ripple.notify.inbound.ratelimit` and `wiring` still say WS-13
  provides one. It was not built.
- The round-2 brief item "DELETE /me asserts ChangeEvent erasure against Postgres
  (slow)" has no test; `test_invariant_I7_delete_me_removes_uploads_and_candidates`
  runs in memory.
- `delivery_tables.py`'s docstring says two racing workers "collide on [the key]
  instead of both believing they were first"; `ON CONFLICT DO NOTHING` reports no
  collision to either, and both have already sent.
