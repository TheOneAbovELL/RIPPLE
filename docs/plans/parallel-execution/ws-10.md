## Plan (written before implementation, CLAUDE.md "How we work" step 2)
Owned paths: `src/ripple/notify/inbound/**`, `src/ripple/api/routers/telegram.py`,
`src/ripple/worker/telegram_poll.py`, `tests/notify/test_inbound*.py`,
`tests/api/test_telegram*.py`, `docs/adr/0075-0079`, `docs/learning/telegram-bot.md`, this file.

Modules, in build order (each lands with its tests):
1. `inbound/updates.py` — strict Pydantic subset of a Telegram `Update` (message text,
   chat, from, callback_query); `parse_update(raw, dropped)` returns a normalised
   `IncomingText | IncomingCallback` or `None` and counts every drop by reason.
2. `inbound/ratelimit.py` — `RateLimiter` protocol (`allow(key, limit, window)`),
   `InMemoryRateLimiter(clock)` sliding window. WS-13's Redis limiter satisfies the protocol.
3. `inbound/ledger.py` — `UpdateLedger` protocol (`first_sight(update_id) -> bool`),
   `InMemoryUpdateLedger` (bounded LRU). Postgres table reserved as migration 0008.
4. `inbound/keyboards.py` — inline keyboards and the callback-data codec
   (`a:s|n|c:<memory id>` for answers, `f:y|n:<memory id>` for forget; ≤ 64 bytes).
5. `inbound/render.py` — `ConversationReply` to chat text: body, `[n]` footer with memory
   ids, "(unconfirmed)" on flagged citations; question cards; 4096-character chunking.
6. `inbound/dispatcher.py` — `InboundDispatcher.handle(update) -> Outcome(replies,
   callback_ack)`: commands, unlinked-chat refusal, link with rate limit, questions and
   callback answers through `ripple.core.answers`, two-step forget, export pointer,
   opening detection to `Services.opening_parser/opening_recorder`, everything else to
   the conversation agent. Pure: it returns replies, it never sends.
7. `inbound/telegram.py` — `TelegramBotApi`: sendMessage (with reply_markup),
   answerCallbackQuery, getUpdates, setWebhook over the same httpx client and token
   handling as `TelegramTransport` (composition; the outbound transport is reused for
   plain text so one transport serves digests and replies). Named `telegram.py` because
   the notify I6 scan allows httpx only in files of that name.
8. `inbound/channel.py` — `TelegramChannel.receive(raw)`: ledger → parse → dispatch →
   deliver; shared by the webhook route and the poll loop.
9. `api/routers/telegram.py` — `POST /telegram/webhook`: secret header check (401),
   200 fast, processing inside the request under a hard timeout; `install_telegram_webhook(app, webhook)`.
10. `inbound/register.py` — `python -m ripple.notify.inbound.register --url …` (setWebhook).
11. `worker/telegram_poll.py` — development long-poll loop over getUpdates.

Tests: `tests/notify/test_inbound_updates.py`, `_ratelimit.py`, `_ledger.py`,
`_keyboards.py`, `_render.py`, `_dispatcher.py`, `_telegram_api.py`, `_channel.py`,
`_invariants.py` (I5, I6 named tests), `tests/api/test_telegram_webhook.py`,
`tests/notify/test_inbound_poll.py`.

## Integration done at checkpoint C3 (coordinator)
- `ripple.api.wiring.app_from_env` turns the channel on when TELEGRAM_BOT_TOKEN is set:
  it requires TELEGRAM_WEBHOOK_SECRET at start-up, mounts `/telegram/webhook` at build
  time (new `mount_telegram_route`) and attaches the channel in the app's lifespan
  (new `attach_telegram_webhook`), where the Postgres checkpointer, the Conversation
  agent over the API's own Services (one router, one retriever) and the bot client are
  opened and closed. `install_telegram_webhook` keeps its behaviour (both steps).
- `.env.example` gained RIPPLE_DASHBOARD_URL; CLAUDE.md lists the poll loop and the
  register command. Caddy already routed `/telegram/*`.

## Open problems
- The update ledger and the bot's rate limiter are in memory: one uvicorn process today
  (infra/entrypoint.sh), so they are correct while it runs, but a restart forgets which
  update ids were handled; Telegram's redelivery after a restart can repeat a reply.
  Postgres ledger: migration id 0008 is reserved. The API's Redis limiter (ADR-0098)
  has a different interface (`take(key, bucket, now)`), so it does not plug in as the
  inbound `RateLimiter` without an adapter.
- No end-to-end test drives the lifespan with a real checkpointer; covered only by the
  slow suite once a database exists.
